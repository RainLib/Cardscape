# 多卡性能与资源验收

本轮测量使用星炉哨卫真实九部件、九骨骼原画、现有卡框、七张 Mask、真实字标与动作粒子。横斩和施法在基准中循环播放，避免一次性动作结束后把静态画面当作动态压力。卡牌共用一个 WebGL 上下文，保留全部源分辨率及材质；这不是自动小贴图降级场景。

硬件实际为 Windows / Intel UHD Graphics / ANGLE D3D11，画布 1280×900、DPR 1，Electron 44.7.0。Godot 功能验收使用的 RTX 5060 Laptop 结果不参与这份性能对照。隔离窗口不抢焦点，后台节流关闭；磁盘／驱动缓存没有清空。这里的“提交／秒”表示宿主提交渲染的频率，不是显示器实际呈现 FPS。

## 已修复的问题

- 同一上下文中的多个卡牌原先重复上传同一个已解码原画。现在按上下文共享不可变图片，按拥有者计数释放；可写 Canvas、像素和 Mask 保持独立，修改单个别名时分离。不同上下文不会混用纹理句柄。
- 嵌入式绘制的 `canAnimate()` 始终为 false，原来的诊断条件因而每卡每帧调用 `gl.getError()`。CPU 采样显示它占据大部分等待。嵌入式改为显式开启 `canvas.dataset.gpuDiagnostics` 时才查询，默认标记 `unchecked`；宿主基准仍在阶段边界检查 GL 错误，普通编辑器保留诊断。
- 拆层透明区域先做轮廓／Mask 计算，浪费 GPU 工作。两端改为先跳过确定透明的源像素，保留透明区域 Shader、背景替换与程序化框面覆盖。原画、透明 Shader、替换背景、磨砂四组实际 GPU 对照，每组 4,608,000 个通道值全部一致。
- 关闭交互预览时断开 ResizeObserver、移除自身的页面可见性监听和指针处理；释放 CPU Mask／网格缓存，迟到的素材回调不能重新分配 GPU 资源。
- 移除多卡预算“每卡至少 8 个粒子”的下限。省电／均衡／精细场景分别使用 48／128／256 总预算，按可见卡数向下分配；预算不足可为 0。单卡制作参数保持原样。

## 本机对照

同一工程与循环动作、同一测量函数的单轮 8 秒对照，双方开启相同的 CPU／GPU 采样。不是跨硬件承诺，也不是冷启动基准。

| 4 卡指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 提交／秒 | 16.8 | 24.4 |
| CPU 提交 P95 | 83.6 ms | 7.9 ms |
| GPU 计时样本 P95 | 64.9 ms | 46.2 ms |
| 请求的纹理存储 | 398.3 MiB | 128.3 MiB |

GPU 时间使用异步 [EXT_disjoint_timer_query](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query/)，丢弃 disjoint 样本，不用 `gl.finish()` 强制同步。纹理／缓冲字节数来自 GL 分配请求，不能视为驱动实际显存。进程工作集／私有内存另行采样；Windows 的 DedicatedUsage／SharedUsage／TotalCommitted 另存为 GPU 进程计数。[Microsoft 对 GPU 内存口径的说明](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)解释了专用、共享及跨进程重复计数，不能把进程私有内存当作显存，或把各进程共享量相加当作设备总量。

短测覆盖三档单卡、4／8／16 卡、3072×4608（约 14 MP）背景，以及每动作 16 组事件。大图由同一真实背景放大，仅用于资源压力，不代表增加了画面细节；该场景使用可写 Canvas，因此按拥有者保留独立存储。每组检查暂停后不绘制、不分配，销毁后 GL 纹理／缓冲／程序／Shader 计数归零。

卡牌按固定画布排布并随数量缩小；矩阵不是固定单卡屏幕面积下的线性扩容对照。窄屏页面另按实际宽高排布，已检查四卡不会从左右边缘被裁掉。

8 卡首次 10 分钟长测取得 576 个资源快照：纹理 152.3 MiB、缓冲约 2.9 MiB，分配与上传计数在测量窗口内不变；反复创建／销毁十次后 GL 对象归零。提交约 13.6 次／秒，仍受 GPU 绘制负担限制。JS 堆随 GC 波动，不能把瞬时堆峰值或 GL 计数稳定称为整个程序永不泄漏。最终含 Windows GPU 计数的复验与测试证据见下方产物索引。

最终 10 分钟内存复验取得 575 个快照，纹理／缓冲／分配／上传计数仍不变；销毁并 GC 后 ArrayBuffer 后备存储由约 57.3 MiB 降至 15.2 MiB。Windows GPU 计数 20 个有效、1 次启动查询超时，共享量约 558–753 MiB 波动，末段约 567 MiB，专用量为 0；这与 152.3 MiB 的逻辑纹理分配口径不同。复验早段同时运行过单元测试，CPU／吞吐数据不参与优化对照。完整摘要与源码摘要见 [测量记录](performance-results-2026-11-03.json)。

## Godot 多卡、CPU 热点与资源验证

原生基准使用同一星炉哨卫真实导出，每卡九个蒙皮部件，交替循环施法和横斩动作，整个场景的粒子预算为 128。多张实例共享同一套原画，不能据此推定十六张不同原画的资源量。窗口 1280×900，按卡数排布并缩小卡片，关闭 VSync，处理帧上限为 30。固定高清与小图保留特效，自动模式按投影宽度选择贴图并遵循保存的特效策略；八／十六卡自动档关闭粒子，人物动画继续。没有混入首次导入、建卡、预热、截图或换档耗时。

固定姿态重放使用保留的旧 SDK 和当前 SDK，八／十六卡三档共六张 1280×900 实际 GPU 图像的原始像素 SHA-256 全部一致，见 `qa/godot-performance/native-optimization-parity.json`。该比较独立于不同启动时长的播放测量窗口。另在真实 28 个表面验证 30 种材质编号、独立正背面值、替换背景与叠加表面、游戏实时属性及小图效果开关，见 `qa/godot-uniform-updates.log`。已查看十六卡自动档实际画面。

资源计数来自 Godot 引擎，不是 Windows 驱动显存。小图使引擎纹理估算约 204→114 MiB；全部卡片释放后约 84 MiB 的引擎／库基础资源仍存在，不据此判定泄漏。共享库、视口与已加载素材不会因为销毁一个卡牌节点而全部卸载。渲染 CPU 计时是视口渲染时间加帧准备时间，不包含脚本全部耗时；`TIME_PROCESS` 监视器可延迟更新，原始 P95 含初始化残留，不能用它替代稳态脚本 CPU 分析。计时口径参照 [RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html) 与 [Performance](https://docs.godotengine.org/en/stable/classes/class_performance.html) 文档。
